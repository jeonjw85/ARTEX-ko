# 취약점 및 다중 트래픽 증거

취약점 세부정보의 "관련 트래픽"은 페이지 간 다중 선택, 목적 및 설명, 정렬 및 바인딩 해제를 지원합니다. 또한 트래픽 페이지에서 여러 레코드를 선택하고 이를 한 번에 하나의 기존 취약점과 연결할 수도 있습니다. 작업에 의해 상속된 취약점 증거는 읽기 전용이며 수정하려면 소스 작업을 입력해야 합니다.

시스템 설정의 "Agent 자동 바인딩 트래픽"은 기본적으로 꺼져 있으며 인터페이스는 `/api/settings`의 `agent_traffic_binding`를 읽고 수정합니다. 활성화하면 쿼리 요청/응답, 도구 호출 및 프롬프트 단어로 인해 발생하는 Token 소비가 증가합니다. Agent의 다음 라운드에서는 새로운 설정을 사용합니다. 닫히면 자동 바인딩 매개변수 및 재바인딩 도구가 숨겨지고 자동 바인딩 지침이 삽입되지 않으며 실행 중인 세션에서 새로 제출된 자동 바인딩이 거부됩니다. 수동 바인딩, 트래픽 캡처, 저장된 증거 읽기 및 내보내기는 영향을 받지 않습니다.

켜진 후 기본 프로세스는 "데이터베이스 검색 → 보고서 자동 실행 Agent → 트래픽 확인 및 바인딩 → 최신 증거 버전에 따라 보고서 작성"입니다. 보고자는 확인 명령, 주요 출력, 기존 실제 트래픽 ID 및 그 목적을 `evidence`에 보관합니다. 취약점 내역 및 실행 기록을 기반으로 Agent를 보고하고, `traffic_search` / `traffic_get`로 이를 검증한 후 `bind_finding_traffic`를 호출한 후 최신 `version`를 읽어 보고서를 저장합니다. 스위치가 꺼지면 보고서 Agent가 추가 원시 트래픽 검색/읽기 도구를 얻지 못하거나 자동으로 바인딩되지 않습니다. 수동으로 바인딩된 스냅샷을 읽고 보고서를 생성하는 것은 여전히 ​​가능합니다.

기존 호출자와 호환 가능: `report_finding`의 `traffic_refs` / `evidence_hint_id`는 여전히 명시적으로 즉시 바인딩될 수 있습니다. 선택적 바인딩: TCP 등 HTTP 이외의 취약점이 수집되지 않거나 정확한 기록을 찾을 수 없는 경우 참조를 생략해도 정상적으로 보고 및 작성할 수 있습니다. 명령 출력, 로그 및 기타 검증 가능한 증거를 보관합니다. 바인딩되지 않은 이유를 설명하고 필수 항목을 추가하지 않는 것이 좋습니다. 제출된 모든 ID는 유효해야 하며 텍스트가 완전해야 합니다. 그 중 하나라도 실패하면 바인딩 작업이 롤백됩니다. 바인딩 실패에 대한 명시적인 보고가 발생하면 전체 보고서가 롤백됩니다. 동일한 스냅샷을 반복적으로 추가해도 바인딩이 증가하지 않으며 설명을 덮어쓰지 않습니다.

## Agent 번호 및 보고서 버전

`report_finding`는 선택적 매개변수를 추가하며 배열 순서는 초기 증거 순서입니다.

```json
{
  "traffic_refs": [
    {"traffic_id": "실제 교통 ID", "role": "baseline", "note": "일반 계정 요청"},
    {"traffic_id": "또 다른 실제 교통 ID", "role": "proof", "note": "복제요청"}
  ]
}
```

용도는 `baseline`(일반 제어), `proof`(취약성 증명), `verification`(보조 검증), `supporting`(보조 증거, 기본값)입니다. 먼저 `traffic_search` / `traffic_get`를 사용하여 실제 기록을 확인하세요. 도메인 이름과 시간은 후보자 심사에만 사용되며 업무 소유권은 추정되지 않습니다.

프롬프트 단어는 [CyberStrikeAI의 취약점 보고 도구 가이드](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)를 참조하세요. 이 프로젝트의 선택적 바인딩 규칙과 결합되어 패키지가 없기 때문에 필수 검증이 도입되지 않습니다. ID를 추측해서는 안 되며, 패치 패킷에 대해서만 프로브를 반복해서도 안 됩니다.

반환된 첫 번째 줄은 여전히 ​​`finding recorded: <노드 탐색 ID>`입니다. 그러면 JSON는 독립적인 취약점 레코드 `finding_id`, 탐색 노드 `finding_node_id` 및 바인딩 요약을 제공합니다.

- `get_finding_traffic(finding_id)`는 **독립적인 취약성 레코드 ID**를 사용하여 정렬된 목록과 `version`를 반환합니다. `binding_id`, `side=request를 전달합니다.|response`、`offset`、`length` 세그먼트 단위로 읽을 수 있으며 각 세그먼트는 최대 8192 바이트。
- `update_finding_report`의 `finding_id` **탐사 노드 ID**를 계속 사용합니다. 실제 읽기 버전을 채우기 위해 `evidence_version`를 추가했습니다. 생성 중에 증거가 변경되면 이전 버전이 거부되므로 다시 읽고 생성해야 합니다.
- 이전 보고서가 전송되지 않은 버전을 호출할 때 기존 교통 증거를 포함한다고 주장하지 않습니다. 바인딩, 설명, 사용법 또는 순서가 변경된 후 업데이트해야 함을 나타내는 보고서가 있습니다.

자동 바인딩을 활성화한 후 `add_hint` / `add_task_hint`는 단일 프롬프트 또는 일괄 `hints`의 각 요소에 `traffic_refs` 저장을 지원합니다. Planner는 `evidence_hint_id`를 대신하여 보고될 수 있습니다. 이 작업에 해당하는 프롬프트에서 참조를 명시적으로 선택합니다. 상속 프롬프트는 인용할 수 없습니다. 시스템은 도메인 이름, 시간 또는 검색 기록을 기반으로 바인딩을 추측하지 않습니다. 실패한 제출은 부분적인 취약점이나 조기 트리거 보고서를 생성하지 않습니다.

놓친 기존 취약점이 있는 경우 다시 등록할 필요 없이 `bind_finding_traffic(finding_id, traffic_refs)`를 사용하여 수정할 수 있습니다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`는 명시적인 `finding_id` 및 `finding_node_id`를 반환합니다. 이전 `id`는 탐색 노드 의미 체계를 유지합니다.

시작 시 이전 도구 schema에 선택적 속성만 추가되고 원래 기본 트래픽 도구 바인딩은 Agent를 보고하도록 확장됩니다. 리바인딩 도구는 기본적으로 Agent를 보고합니다. 사용자 정의된 바인딩 목록, 프롬프트 단어, 설명 및 활성화된 상태 보존. 최종 도구가 완성된 후 지침이 추가됩니다. 보고 역할은 기존 증거를 전달하는 역할을 담당하고 보고 역할 Agent는 보고서 확인, 제본 및 작성을 담당합니다. 플랫폼 대화에 작업 컨텍스트가 부족한 경우 구조화된 프롬프트를 통해 작업 Agent로 전달되어야 하며 직접 보고되어서는 안 됩니다. 업무가 완료되었다고 판단하기 전에 기존 증거를 인계해야 합니다. 패키지가 없으면 기다릴 필요가 없습니다. 실패한 `report_finding`는 Agent 보고서를 트리거하지 않습니다.

## API

기본 경로: `/api/exploration/findings/{finding_id}/traffic`, 독립적인 취약점 ID를 사용합니다. 인증 상속; `context_task`는 작업 가시성과 상속을 읽기 전용으로 확인합니다.

| 메서드/상대 경로 | 요청/반품 |
| --- | --- |
| `GET` | 순서화된 요약, 증거 버전, 보고서 채택 버전 |
| `POST` | `{"traffic_refs":[...]}` 정비 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명하다"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 전체 목록이어야 합니다. |
| `GET /{binding_id}` | 스냅샷 메타데이터 및 경계 텍스트 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1` 전체 원본 바이트 다운로드 |

버전/정렬된 컬렉션 충돌, 아카이브에 쓰면 `409`가 반환됩니다. 상속된 쓰기 `403`; 존재하지 않거나 취약점 `404`가 아닌 바인딩; 트래픽/첨부 파일 읽기 및 확인 실패는 분명히 오류를 반환합니다.

## 저장 및 마이그레이션

멱등성 마이그레이션 PostgreSQL 시작: `traffic_evidence_snapshots`, `finding_traffic_bindings` 및 `findings.evidence_version`/`report_evidence_version`(기본값 0)를 추가합니다. 역사적인 텍스트를 기반으로 추측하지 마십시오.

스냅샷은 원본 트래픽 ID, 수집 시간, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이 및 SHA-256를 저장합니다. 본문은 정리 가능한 `data/traffic`와 별개로 `<data>/evidence/blobs/<상위 2개>/<hash>.bin`에 해시되며 여러 취약점이 스냅샷/텍스트를 공유할 수 있습니다. 스냅샷은 콘텐츠 업데이트 인터페이스를 제공하지 않으며 확인이 일관되지 않으면 읽기 및 내보내기가 실패합니다.

큰 텍스트 blob 및 이전 디렉터리 레코드를 포함하여 원래 트래픽 쓰기 잠금 아래의 전체 텍스트를 읽습니다. 먼저 파일을 유지하고 확인한 다음 단일 PostgreSQL 트랜잭션을 사용하여 탐색 노드, 의도 관계, 취약점, 스냅샷 및 바인딩을 작성합니다. 제출 후 기획자에게 통보됩니다. 실패하면 참조 파일이 남지 않을 수 있지만 부분적인 비즈니스 기록은 생성되지 않습니다.

PostgreSQL advisory lock `7337741004`는 증거 파일과 SQL 참조를 조정합니다. 작업 라인 잠금은 아카이브가 대기열에 추가된 후 증거 수정을 금지합니다. 복구는 텍스트 설치부터 메타데이터 제출까지 전체 프로세스에 걸쳐 증거 잠금을 유지합니다. 취약성 계단식 삭제는 바인딩을 제거합니다.

클리너는 매시간 실행되며 참조가 없고 진행 중인 작업이 아닌 콘텐츠만 회수하며 최소 지연 시간은 24시간입니다. 일반 트래픽 정리는 증거 디렉토리를 건드리지 않습니다. 핫 데이터를 백업할 때 PostgreSQL와 `data/evidence`를 동시에 백업하세요.

## 내보내기 및 보관

Markdown에는 주문된 증거 목록과 버전이 포함되어 있습니다. JSON에는 메타데이터가 포함되어 있습니다. CSV는 수량을 늘려 ID를 묶습니다. `md-zip`는 취약점 Markdown를 유지하며 다음을 제공합니다.

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown는 상대 링크를 통해 메시지를 참조합니다. 다운로드를 위해 전송하기 전에 모든 ZIP 항목에 대한 첨부 파일 복사, 해시 확인, 압축, 디스크 동기화 및 CRC 읽기 확인을 완료합니다. 항목이 누락되거나 손상된 경우 전체 다운로드가 실패하게 됩니다. 완전한 첨부 파일은 바이너리 원시 바이트를 유지합니다.

Archive v3는 원본 트래픽이나 도메인 이름에 의존하지 않고 취약점 바인딩 관계에 따라 스냅샷과 텍스트를 수집합니다. 핫 데이터는 패키지 검증이 완료된 후에만 삭제됩니다. 공유된 증거는 계속 유지됩니다. 복구 중에 설치 텍스트를 먼저 확인한 다음 메타데이터와 바인딩이 복원됩니다. 실패 재시도가 지원됩니다. v1/v2는 계속 복구 가능하며 누락된 새 필드는 명시적으로 0으로 채워집니다.

## 검증 및 경계

`ARTEX_PG_DSN`로 지정된 각 테스트 패키지에 대해 독립적이고 새로 생성된 PostgreSQL 테스트 라이브러리를 설정하여 잔여 작업/모델 고정 장치가 백그라운드 실행을 트리거하는 것을 방지합니다. 관련 패키지의 전체 테스트를 실행하고 구성 누락으로 인한 건너뛰기가 없는지 확인합니다.

```sh
# 각 패키지를 실행하기 전에 ARTEX_PG_DSN를 해당 독립 테스트 라이브러리로 설정하십시오. 명시적인 구성이 실패하면 오류가 보고되어야 합니다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트 엔드 검증에는 영향을 받는 파일의 `npx tsc --noEmit`, Biome 검사, Webpack 빌드 및 `NEXT_EXPORT=1` 정적 내보내기가 포함됩니다. 실행 중인 개발 서비스를 덮어쓰지 않으려면 별도의 캐시 디렉터리를 사용하세요.

기본 종단 간 수용은 독립 포트, 제어된 HTTP/도메인 이름 HTTPS 대상 및 임시 데이터 디렉터리를 사용하여 두 개의 바인딩 항목, 페이지 간 선택, 정렬/설명, 오류 프롬프트, 읽기 전용 상속, 다운로드 및 내보내기, 보관, 핫 텍스트 재활용, 원본 트래픽 삭제 후 해시 복구 및 확인을 포함합니다.

첫 번째 버전은 전역 증거 조정 잠금을 사용합니다. 대규모 일괄 바인딩/내보내기 또는 느린 첨부 파일 다운로드 중에는 다른 증거 작업이 기다릴 수 있습니다. 녹음 기록이나 완전한 텍스트가 없으면 증거를 만들 수 없습니다. 이 기능은 캡처 스위치를 변경하지 않으며 IP에 직접 액세스하는 HTTPS의 인증서 발급을 처리하지도 않습니다.
